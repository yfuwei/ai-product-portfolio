01 / 产品判断

五个不太讨喜的AI 产品判断：

01｜客服 AI 最值得解决的，可能不是客服的问题。

这不是客服回答得不够好，而是企业把“答复”当成了“处理”。

客户第三次催退款。AI 第三次准确解释退款政策，语气礼貌、答案完整。可周三承诺的仓库核查，到了周五仍然找不到可追踪的任务。

客户第三次催退款。AI 第三次准确解释退款政策，语气礼貌、答案完整。

可周三承诺的仓库核查，到了周五仍然找不到可追踪的任务。

这不是客服回答得不够好，而是企业把“答复”当成了“处理”。

P2 没有继续打磨客服话术，而是设计了一条服务续办链：恢复历史承诺，找回同一笔退货的未完成事项，交给 Agent Workflow 推进仓库核查，再根据业务结果接续退款处理。

WH-201 Waiting 就是还在等，RF-301 Started 也不等于退款完成。不能因为 AI 参与了处理，就把任务进展包装成业务结果。

客户需要的不是一个更会道歉的机器人，而是有人把事继续办下去。

02｜RAG 最大的问题，可能根本不是幻觉。

最有欺骗性的错误，不是 AI 编造了证据，而是它拿真实证据说错了话。

一份过期制度可以是真的，一条历史案例也可以有准确出处。AI 把它们引用得越漂亮，用户越可能相信一个根本不适用于当前业务的结论。

一份过期制度可以是真的，一条历史案例也可以有准确出处。

AI 把它们引用得越漂亮，用户越可能相信一个根本不适用于当前业务的结论。

最有欺骗性的错误，不是 AI 编造了证据，而是它拿真实证据说错了话。

P1 的检索测试暴露过类似风险：历史材料可能因语义更接近问题而进入高位候选。我没有优先增加 Rerank，而是先调整 Retrieval Scope 和 Metadata，区分有效制度、区域规则与历史参考。

随后设计独立的 Eligibility 判断，检查证据是否真正适用于当前任务。

我宁愿 AI 明确告诉用户“这份资料不能用于当前项目”，也不愿它给出一篇引用完美的错误建议。

03｜多 Agent 有时候不是架构升级，而是责任稀释。

每个 Agent 都完成了自己的工作，不代表客户的事情有人负责到底。

仓库核查要等三天。期间业务状态可能改变。事件回来之后，谁重新核实？谁决定继续退款处理？谁保证不会重复建单？

Warehouse Agent 查仓库，Refund Agent 查退款。两个 Agent 都完成了自己的查询。

然后呢？

仓库核查要等三天。期间业务状态可能改变。事件回来之后，谁重新核实？谁决定继续退款处理？谁保证不会重复建单？

每个 Agent 都完成了自己的工作，不代表客户的事情有人负责到底。

P2 的设计让 Service Orchestrator 持有持续的服务目标、等待状态与计划版本。仓库事件不能直接代表核查完成；等待解除后，Refund Agent 还必须重新查询已有任务，才能决定接续还是创建。

但这仍然不能证明三个 Agent 就是最佳架构。

如果一个 Workflow 加两个工具就能更可靠地完成这些事，我会毫不犹豫地砍掉多余的 Agent。

多 Agent 的价值必须由任务结果证明，而不是由架构图上的方框数量证明。

04｜完整的企业知识本体，可能是一场昂贵的自我感动。

AI 产品还没证明自己值得做，支撑它的基础设施已经成了最大的项目。

AI 需要理解制度版本、区域规则和历史案例之间的关系。于是开始统一词表、定义完整 Schema、建设领域 Ontology、规划企业知识图谱。

AI 需要理解制度版本、区域规则和历史案例之间的关系。

于是开始统一词表、定义完整 Schema、建设领域 Ontology、规划企业知识图谱。

听起来很有远见。

但原本只需要解决几条关键业务关系，最后可能演变为一项长期的知识基础设施工程。

AI 产品还没证明自己值得做，支撑它的基础设施已经成了最大的项目。

P1 最终选择只保留当前任务需要的最小 Knowledge Graph 关系层，停止完整 Domain Ontology 的建设计划，并选择集成成熟 Wiki 能力的产品路线。

不是所有可能有用的能力，都值得自己造一遍。

我不反对建设底座，但拒绝让底座把产品吃掉。

05｜Human-in-the-loop，也可能只是产品团队推卸责任的借口。

企业没有得到自动化，只是多了一条等待签字的流水线。

担心 AI 判断不准？加一道人工确认。担心 Agent 执行失控？再加一道审批。系统不知道如何处理异常？全部转人工。

担心 AI 判断不准？加一道人工确认。

担心 Agent 执行失控？再加一道审批。

系统不知道如何处理异常？全部转人工。

最后 AI 负责生成建议，员工负责逐条核对、反复点击，还要为点错的那个按钮承担责任。

企业没有得到自动化，只是多了一条等待签字的流水线。

以 P2 的拟议流程为例，仓库事件到达后的只读复查、有效记录核验、既有任务查重，应该尽可能通过工具和明确规则完成。证据冲突、授权不足或高影响业务动作才需要升级人工处理。

P1 也是如此。证据没有使用资格，系统就应该拒绝形成确定结论，而不是把一个未经核验的判断扔给员工，让他“确认一下”。

如果一道人审说不清自己究竟要拦截哪种错误，它就不是治理，而是责任转移。

02 / 核心项目

把判断放进产品。

业务智能助手

RAG · Agent · 可信上下文 · 知识图谱 · Ontology · Wiki

资料是真的，AI 也可能给出不该给的结论。

现行制度、旧版本、历史案例都能被 RAG 找到。检索相关，不代表业务适用。

任务上下文、Agent 调用控制、证据准入：管住知识进入业务判断的最后一步。

知识图谱只留最小关系层；完整 Ontology 停建；Wiki 选择成熟能力集成。

AI 智能客服与多 Agent 服务工作流

智能客服 · Workflow · Multi-Agent · LangGraph

第三次催退款，AI 不该第三次从头回答。

客户第三次催退款，前次承诺的仓库核查仍没有可追踪的后续任务。真正断掉的不是对话，而是任务。

跨会话恢复服务目标，主编排协调仓库与退款 Agent；用 Workflow 接住异步等待、事件恢复和动态重规划。

Agent 可以分工，任务不能断链。等待不丢、续办查重、状态不冒充结果。
