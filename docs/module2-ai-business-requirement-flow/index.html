项目 02｜AI 智能客服与多 Agent 服务工作流

第三次催退款，接着办上次没办完的事。

客户第三次追问同一笔退款。AI 关联此前的客服承诺、物流与仓库记录，恢复未完成的核查任务，再由仓库与退款 Agent 接续处理并更新进展。

PRODUCT STORY

从催问，到续办。

一笔退货退款，四个产品切面。

  1. A01三次咨询，一个问题看见业务断点→
  2. A02关联业务，恢复任务恢复未完成任务→
  3. A03Agent 协作与重规划并行执行，按结果改变计划→
  4. A04从执行到服务进展服务已推进，到账待确认→

A01｜三次咨询，一个没解决的问题

客户一直在问同一笔退款，服务却没有持续推进。

产品判断重复咨询是同一任务的恢复信号，而不是新的问答起点。

A02｜Service Context Linking

三次咨询，AI 找回上次没做完的事。

产品判断AI 不是只关联信息，而是把历史处理记录恢复成可以继续执行的任务。

A03｜Multi-Agent Execution & Replanning

找回任务之后，AI 开始组织工作。

产品判断规划要能消费异步结果，才能接续跨部门的业务任务。

A04｜从 Agent 执行到服务进展

从重复回答，变成持续推进同一个服务任务。

产品判断服务进展按已完成的动作与仍待完成的业务分开呈现。

异步延伸 / FLOW B

同类退款 Case 若反复卡在相似仓库节点，可关联服务事件，形成运营调查的候选问题。

查看退款续办的详细设计、核心界面与待执行验证方案。

B01｜业务场景与产品定义

让 AI 接续一笔反复被催办的退款，而不是重新回答一次。

以电商退货退款的重复催办为切片，把历史承诺恢复为可执行任务，跨仓库与退款业务域持续推进。

SIMULATION · 模拟业务场景｜产品方案设计与前端演示，不代表真实企业调研、生产运行或已验证业务结果。

1.1 业务故事

  1. 周一CONV-001
    询问退款周期

    客户咨询退货寄回后多久退款，客服解释正常周期。

  2. 周三CONV-002
    签收了，为什么还没退？

    物流已投递，退款尚未发起。客服承诺：“帮您安排仓库核查”。

  3. 周五CONV-003
    追问上次承诺的进展

    “上次不是说帮我去仓库查吗？现在怎么还是没消息？”

RET-001 · 同一笔退货退款 / 初始快照

物流 已投递 · 仓库 未确认收货 · 退款 尚未发起

任务断点：没有找到可关联的有效仓库核查任务。

第三次来访的目标是让此前的核查继续推进。断开的不是回答，而是承诺之后的执行与追踪。

1.2 用户与任务

主要用户 / 企业侧
企业客服人员 / 智能客服运营团队：在客服工作台查看关联记录、Agent 执行情况与当前待续办事项，跟踪处理结果。
服务对象 / 客户侧
反复催办退款的客户：从在线智能客服发起咨询，并在这里收到任务进展。
执行角色
Service Orchestrator 组织计划；Warehouse Agent 核查仓库；Refund Agent 推进退款后续处理。

客户再次进入在线智能客服追问退款 → AI 关联历史咨询与售后记录 → 恢复未完成核查 → Agent Workflow 续办 → 客服工作台跟踪，客户收到新进展。

这是同一产品中相互衔接的两个接触面，聚焦退款重复催办的任务恢复与跨部门续办；未实现完整客户聊天系统或真实后台。CASE-001 关联 RET-001，阶段回复不等于退款到账或 Case 已解决。

1.3 产品的 AI 能力

找回同一笔退货的未完成任务Service Context Linking
从三次咨询、RET-001 退货记录、物流与仓库状态中，关联周三承诺，恢复当前待续办的仓库核查。
分派仓库核查与退款核对Multi-Agent Task Orchestration
Service Orchestrator 将仓库核查与退款核对拆成可执行任务，分派两个专业 Agent 并汇总结果。
等到新结果后接续退款处理Task Continuation & Replanning
等待 WH-201 反馈时保留任务上下文；核实入库后更新计划，再交给 Refund Agent 推进退款处理。

三项能力共同服务于同一条退款续办工作流。

1.4 企业 Ontology 前提

前提：企业已有客户、会话、退货、物流、仓库、退款与服务任务的基础关联关系（Ontology / Metadata）。P2 利用这些关系查询记录与续办任务，不建设底层关系能力。

这是独立于 P1 的假设，不代表 P1 已提供这套业务关系，也未完成真实集成。

1.5 MVP 边界

聚焦同一客户、同一笔退货退款、多次咨询，以及客服、仓库与退款业务域之间的任务续办。

本次退款续办

  • 关联历史目标，读取业务状态并检查已有任务。
  • 创建或接续仓库核查，异步等待并恢复执行。
  • 按新结果分派退款后续任务，生成客户可理解的进展。

暂不包含

  • 其他客服意图与全量售后流程；退款支付与结算执行。
  • 真实业务系统集成、Ontology 基础设施建设。
  • 真实 LangGraph Runtime 或生产 Agent 执行。

B02｜Multi-Agent Workflow 设计

从历史任务恢复，到跨 Agent 执行与动态重规划。

把周五的追问转为可继续执行的服务任务，说明谁来做、工具返回什么，以及新结果如何改变下一步。

方案设计 + 模拟业务数据｜下文 Trace 为预期执行过程，业务工具与 Agent Runtime 均未真实接入。

2.2 Service Orchestrator：规划与任务分派

Orchestrator 接收 CASE-001 的目标：继续核实这笔退货的仓库收货情况，并根据结果推进退款处理。初始记录为物流已投递、仓库尚未确认收货、退款未发起，且尚未找到可关联的有效仓库核查任务。

Service Orchestrator · Plan v1 / 同批并行查询

查清仓库收货差异

Warehouse Agent

查明物流签收却未确认入库的原因，检查已有仓库核查任务，并推进有效核查。

核对退款与续办条件

Refund Agent

核对退款是否启动、有无已有处理任务，以及当前是否具备继续处理的业务条件。

两项任务先并行查询。Warehouse Agent 返回核查任务与收货待核实事项；Refund Agent 返回退款现状与待满足条件。仓库入库尚未确认时，退款后续处理先等待核查结果。

Plan v1 定义当前需核实的事项与预期结果，不假定仓库已收货，也不预设必须新建退款任务；具体动作取决于各 Agent 查到的业务记录。

2.3 专业 Agent 与业务工具执行

CASE-001 的初始并行查询中，Warehouse Agent 补上缺失的核查，Refund Agent 先返回退款现状；收货核实后，同一 Refund Agent 再次接到续办任务。

WAREHOUSE AGENT · 模拟执行设计

查明签收与入库差异，推进收货核查

  1. 查询物流投递记录：已投递。
  2. 查询仓库入库记录：尚未确认收货。
  3. 检查 RET-001 的已有仓库核查任务：未找到有效任务。
  4. 调用 仓库核查任务工具，创建 WH-201。
  5. 返回 Orchestrator：WH-201 已创建，等待仓库反馈；收货仍待核实。

异步反馈后：按 WH-201 定位仓库记录 → 重新查询入库 → 取得有效入库记录 → 返回核查完成的 任务结果。

REFUND AGENT · 模拟执行设计

核对退款进展，确定已有任务是否需接续

  1. 查询退款记录：尚未发起。
  2. 查询关联退款处理任务：主场景未找到有效既有任务。
  3. 核对当前条件：仓库尚未确认收货，暂不进入退款异常续办。
  4. 向 Orchestrator 返回退款事实、任务查询结果与待满足的收货确认条件。
Plan v2 再次分派
  1. 核对已经确认的仓库收货记录，并重新查询退款状态。
  2. 检查是否存在可以接续的退款异常处理任务。
  3. 未找到有效既有任务，调用退款异常任务工具创建 RF-301。

2.4 异步等待、事件恢复与继续执行

WH-201 创建后，仓库核查并不会立即完成。Workflow 进入 Waiting，保存目标、任务与当前计划；后续仓库事件唤回这条工作流，Warehouse Agent 再核实入库记录。

暂停的是工作流执行，保留的是任务上下文；等待期间 LLM 不持续运行，也不不断生成回答。

Waiting 保存与事件恢复契约 Task State / 关联键 / 恢复条件
保存内容
服务目标、待完成子任务、WH-201、已完成查询及来源、预期仓库事件、Plan v1 与各分支结果。
事件关联
应用层以客户范围 + RET-001 + WH-201 定位 CASE-001 的持久化执行线程；保存事件 ID / 时间，去重后请求恢复。
恢复条件
关联唯一且记录可核对；Warehouse Agent 获取有效入库依据后产出 Task Result。无法关联或记录仍不明确时保持待核实，不直接推进退款。
实现分工
拟用 LangGraph 保存执行状态及恢复；应用层负责事件接入、业务 ID 映射与任务状态。外部任务不会因图执行暂停而自动完成。

2.5 Dynamic Replanning

仓库未确认

若仍未确认实际收货 → 继续 WH-201，不启动 Refund Follow-up。

另一种执行结果｜发现已有退款任务

独立模拟分支，不属于上方主场景的执行历史。发生于 Plan v2 分派之后、Refund Agent 执行退款任务的过程中。

  1. 新发现

    Refund Agent 在另一条售后记录中找到疑似关联的退款异常任务，尚未直接关联到 CASE-001。

  2. 核对关联

    查询业务记录，确认是否属于同一笔退货 RET-001、同一未完成退款事项，以及已有任务是否有效、有何处理进展。

  3. 改变行动

    确认有效后，将已有任务与进展返回 Orchestrator，后续计划改为接续该任务并跟踪结果，不重复创建 RF-301。

    若不能证实关联，不直接将疑似任务作为同一事项处理。

2.6 LangGraph / Dify 技术选型

这笔退款续办需要保留任务状态、等待仓库事件并按新结果更新计划，因此拟采用 LangGraph 式状态编排；Dify 保留为可视化原型备选。当前未集成真实 Runtime 或企业业务系统。

选型依据与实现边界
业务要求
多步骤任务、专业 Agent 协作、长周期等待、事件恢复与动态重规划。
拟采用方案
LangGraph：用持久化执行状态与暂停 / 恢复机制承接任务上下文；业务事件接入和动态分派逻辑由应用实现。
选择原因
本项目优先自定义状态、事件与计划更新的关系。该选择是针对本场景的设计取舍，仍需通过实现验证。
备选方案
Dify：可视化 Workflow 与 Agent / 工具节点适合快速验证标准问答、工具查询与有限节点编排。Dify 也能编排工具与 Agent；本方案选择 LangGraph 源于任务续办的控制需求，而非断言 Dify 无法实现。
实现状态
完成产品方案与技术选型；未集成真实 LangGraph Runtime，未连接 WMS / 退款系统，未验证端到端自动执行。
技术依据与待验证事项 官方资料 / 拟议实现

官方机制参考：LangGraph 持久化状态、暂停与恢复；Dify Agent 节点与可视化 Workflow。

5.4 不只统计回答次数，而是衡量服务任务是否接续

四项口径均待测量，暂无实测数值。先固定纳入规则、真值与观察窗口；分母为零时不计算比例。

M01 · 待测量历史任务关联判断正确率

AI 找回的是正确的未完成事项吗？不相关的历史任务有没有被排除？

具有明确业务对象关联真值、且实际触发历史任务关联判断的模拟或服务样本。

分子正确恢复目标任务，或正确排除不相关历史任务的样本数分母具有人工确认关联真值的历史任务判断样本总数

观察错误退货关联、错误历史承诺、错误续办目标，以及本应排除却被错误恢复的任务。

T01 对应正确恢复，T07 对应正确排除；分子、分母统一按判断样本计数，每个样本只计一次。未恢复不等于正确排除；证据不足、尚无真值的样本单列为待核实，不进入统计。

M02 · 待测量任务有效接续率

恢复目标后，是否产生可追踪的后续动作？

仅纳入符合续办条件、且预先约定的观察窗口已结束的恢复任务。

分子正确进入有效后续执行或接续既有任务的数量分母符合续办条件且观察窗口已结束的恢复任务数量

有效 Waiting 且尚未到观察终点的任务单列，不直接算失败。仅有客服回复，没有可追踪动作，不算接续。

M03 · 待测量事件恢复与重规划正确率

新结果是否正确改变后续执行？
