A02｜Service Context Linking

B01｜业务场景与产品定义

让 AI 接续一笔反复被催办的退款，而不是重新回答一次。

以电商退货退款的重复催办为切片，把历史承诺恢复为可执行任务，跨仓库与退款业务域持续推进。

SIMULATION · 模拟业务场景｜产品方案设计与前端演示，不代表真实企业调研、生产运行或已验证业务结果。

1.1 业务故事

“上次不是说帮我去仓库查吗？现在怎么还是没消息？”

  • 周三 CONV-002 曾承诺安排仓库核查。
  • 同一笔 RET-001 物流已投递，仓库尚未确认有效入库。
  • 周五未找到有效、可追踪的关联核查任务。

当前业务状态：物流已投递仓库未确认退款尚未发起

1.2 用户与任务

一线客服
找回历史服务事项，查看可追踪执行进展，审核待发送的客户阶段性回复。
Agent 任务跟进人员
查看任务进展、Waiting、异常和当前执行事项，定位需要人工跟进的业务问题。

1.5 MVP 边界

Flow A｜单 Case 服务任务续办（核心 MVP）

围绕 CASE-001，恢复并持续推进同一笔 RET-001 的退款服务目标。

  • 跨会话恢复目标，主编排组织专业查询。
  • WH-201 Waiting；事件恢复后核实有效记录。
  • 更新计划，续办退款异常任务，回传客服待发送草稿。

Flow B｜跨 Case VOC（客户之声）问题发现（独立辅助能力）

比较多条独立模拟 Case 的服务记录，识别重复业务卡点并排除不同处理阶段。

  • 形成候选问题，不把关联当成共同根因。
  • CI-001 · Need Evidence，仍需补证。
  • TASK-001 尚未创建，仅为条件性改进任务预览。

单笔服务记录可沉淀为跨 Case 的分析输入；两套工作流独立运行。

Flow A 产生的记录可成为 Flow B 的数据来源之一；Flow B 使用多个独立 Case，不是 Flow A 的自动下一步，也不阻塞单笔退款处理。

B02｜Multi-Agent Workflow 设计

从历史任务恢复，到跨 Agent 执行与动态重规划。

把周五的追问转为可继续执行的服务任务，说明谁来做、工具返回什么，以及新结果如何改变下一步。

方案设计 + 模拟业务数据｜下文 Trace 为预期执行过程，业务工具与 Agent Runtime 均未真实接入。

2.1 跨会话业务关联与任务恢复

周五的追问，凭什么关联到周三对 RET-001 的核查承诺？

  1. CONV-003当前追问
  2. CONV-002历史核查承诺
  3. RET-001同一笔退货
  4. CASE-001恢复服务目标

为什么关联到 RET-001？

  • 属于同一客户范围，指向同一笔 RET-001。
  • CONV-002 存在明确的仓库核查承诺。
  • 当前未确认入库、缺少核查记录，与这项待续办事项相符。

什么情况需要停止自动关联？

  • 相似催问属于另一笔退货。
  • 无法证明历史承诺属于 RET-001。
  • 业务对象关系冲突。
  • 关联依据不足 → 保留待确认，不执行另一笔退货的任务。

AI 理解“上次帮我查”的指代，提出候选；业务关系定位记录，可信知识依据解释为何仍需核查入库。工具在客户访问范围内核对承诺与事实；相似文本不证明关联，LLM 不补全缺失事实。

2.4 异步等待、事件恢复与继续执行

WH-201 等待仓库核实结果；挂起期间保留任务，不持续调用 LLM。业务事件用于唤起复核，不直接把核查变成完成。

匹配与去重

事件不必携带 WH-201 ID。用 RET-001 等业务对象定位等待任务，核验同一退货与当前任务；去重后再恢复。找不到唯一关联时不自动推进。

核实与回传

有效入库记录确认后，完成 WH-201 并向主编排返回结果；记录仍未有效确认时继续 Waiting 或待核实，不解除仓库阻断。

拟将业务关联键映射到持久化执行线程；应用层负责事件接入、任务定位与去重，框架暂停 / 恢复不能替代业务核验。事件 ID 等为拟议字段，非真实系统日志；映射与恢复正确性仍待验证。

2.5 Dynamic Replanning：条件决策与计划更新

Service Orchestrator · 主编排消费新的有效业务结果，改变下一步行动；事件到达不等于阻断解除。

复查无有效既有退款任务，且续办前提满足需要新的处理事项主场景模拟创建 RF-301。

实际退款尚未发起，到账尚未确认；返回的是客服待发送 Mock 草稿，不是消息送达记录。

独立模拟分支 · 发现疑似既有退款任务

Refund Agent 在另一售后记录中找到疑似任务时，先核对三项业务依据，不与上方 RF-301 新建主场景混成同一次历史：

  • 是否属于同一 RET-001。
  • 是否属于同一未完成退款事项。
  • 任务是否仍有效，有何处理进展。

确认有效后返回 Service Orchestrator，接续原任务并跟踪，不重复创建 RF-301；未确认关联不能直接复用。

计划更新使用新的有效业务事实，不把条件分支描述为完全自主的 LLM 规划。

2.6 LangGraph / Dify 技术选型

拟采用 LangGraph 状态编排。

持续等待
WH-201 等待外部反馈时，保留服务目标、已知结果与 Plan v1。
事件恢复
仓库事件关联原任务后，由 Warehouse Agent 继续复查，不丢失历史上下文。
计划更新
Service Orchestrator 消费核实结果，再调整分派和后续分支。

LangGraph｜拟采用

让应用掌握等待任务的状态、恢复入口与剩余计划分支，承接本场景的具体控制需求。

Dify｜可视化备选

快速验证标准 Agent、工具查询与较固定工作流；不同分支和等待机制需结合实现评估，不断言其无法完成对应能力。

主要取舍：需要对执行状态、暂停 / 恢复、结果消费与分支保留较细的应用级控制。LangGraph 提供持久化与暂停 / 恢复机制；业务事件映射、去重、并行结果汇总与重复建单控制仍由应用逻辑设计，并需验证恢复正确性。

尚未接入真实 LangGraph Runtime 或企业 API，尚未完成事件恢复测试；持久化配置、业务映射、去重与各分支待最小 Mock 执行验证。当前仅为产品方案与模拟状态，没有 Workflow 执行测试结果。

官方机制参考：LangGraph 持久化状态、暂停与恢复；Dify Agent 节点与可视化 Workflow。

BC03 · H02

重复仓库事件：去重后，仍重复完成与重规划

输入冲突
WH-201 已 Completed、Plan v2 已生效；同一已处理事件再次到达，有效入库记录仍在。
首次失败

原因
旧规则去重事件后，只要记录有效就追加完成与重规划动作，未检查任务是否已完成、计划是否已更新。
修正
非 Waiting 任务保持当前状态与计划；只有 Waiting 且记录有效才完成，Plan 已为 v2 时不重复更新。事件去重与状态更新各自设门槛。

PASS：仅 ignore_duplicate_event，保留 Completed / v2。两项重复动作均为 0；这里只验证动作意图，持久化与真实副作用仍待验证。
