项目 01｜企业知识工作台

知识被找到只是开始，被可信使用才是产品。

从可信上下文到 Agent 工作流的产品化演进。

模型都这么强了，为什么企业还需要自己的知识系统？

这个项目不是做一个知识库问答机器人，而是设计一套企业知识工作台：把分散在文档、制度、会议、项目资料和历史经验中的知识，整理成可引用、可追溯、可校验、可进入任务流程的可信上下文。

AI 可以组织知识，但业务判断必须建立在来源、权限、版本和适用范围之上。

01｜业务问题

企业不是缺知识，而是知识不能被可信使用。

企业文档、制度、会议纪要、项目资料和历史经验并不少。真正的断点在于：知识即使被 AI 找到，业务仍然不知道它来自哪里、是不是最新、谁能使用、适不适用于当前判断，因此很难进入方案、复盘或下一步行动。

来源分散

找到了，也不敢用

产品手册、制度、会议纪要和 FAQ 分散在多处，单次搜索很难还原完整依据链。

版本约束

看到了，也未必有效

方案、政策和流程会更新。没有版本与更新时间，内容只能停留在参考。

适用范围

相关，不代表适用

同一句知识可能只适用于特定客户、产品版本、区域或流程阶段。

追溯断点

用了，也难以复核

没有来源、权限、引用和人审入口，输出难以复核，也难进入工作台任务。

企业真正缺的不是更多答案，而是能支撑判断、复核和行动的可信上下文。

02｜贯穿样例 / 用户任务

一次业务判断，需要哪些可信上下文？

先别急着让 AI 回答。一个销售、运营或产品同学准备客户方案、业务判断材料或项目复盘材料时，真正要完成的不是“问 AI 一个问题”，而是基于可信来源整理一份可引用、可复核、可进入下一步行动的上下文。

场景：准备客户方案、业务判断或项目复盘材料

用户不是在问 AI 一个问题，而是在完成一次需要依据、限制和后续行动的业务判断。

  • 当前客户是否适合某个产品能力？
  • 哪些承诺可以引用？
  • 哪些限制必须提前说明？
  • 过去项目里有哪些经验可以复用？
1. 判断任务

明确要完成什么

准备客户方案、业务判断材料或项目复盘材料。

2. 可信来源

找到可用依据

召回与当前判断相关的资料，而不是只找相似文本。

产品手册 制度文件 会议纪要 / FAQ 历史项目 / 过往案例
3. 上下文卡

组织候选上下文

把相关知识整理成带来源、引用、版本和适用范围的候选上下文。

4. 上下文校验

确认能不能用

由人确认来源是否可靠、版本是否有效、范围是否适用。

5. 行动简报

进入工作台任务

确认后的上下文进入方案、复盘或下一步行动材料。

AI 负责召回、归纳和组织上下文；人负责确认来源、版本、适用范围和下一步使用。

03｜可信上下文层

RAG 不是终点，可信上下文才是起点。

上下文卡不是一段 AI 摘要，而是一组进入工作流前必须被检查的使用条件。它让用户先看依据、边界和风险，再决定是否把它放进行动简报。

上下文卡｜候选上下文对象

一张带依据、边界和人审入口的上下文卡

状态：待确认
候选判断

这段知识可能支持当前客户方案中的某项能力说明，但必须先确认来源、版本、适用范围和风险。

证据依据

来源与引用：来自产品手册 v2.1、历史项目复盘、会议 FAQ，并保留可追溯的原文片段或段落位置。

使用条件

权限与版本：当前用户是否有权使用？对应的产品、政策或流程版本是否仍然有效？

适用范围

适用范围与更新时间：适用于什么客户、地区、产品版本或流程阶段？是否可能已经过期？

风险与人审

风险与人审：证据不足、语义相近但场景不同、影响承诺的内容，需要业务负责人确认。

进入工作流前的校验门

01
能不能引用？

有明确来源、原文片段和段落位置。

02
能不能使用？

符合当前用户的权限和有效版本要求。

03
适不适用？

匹配当前客户、场景、地区或流程阶段。

04
需不需要人审？

高风险、低置信或影响承诺的内容必须由人确认。

可信上下文层的价值不是让 AI 多说一点，而是防止知识在没有权限、版本和责任边界的情况下被误用。

04｜AI / RAG 接入前后

RAG 改变的是上下文组织，不是替人判断。

AI 接入后的价值不是给出一个看似完整的聊天回答，而是把分散知识整理成可复核、可确认、可进入工作流的候选上下文。

接入前

人手动翻资料

在产品手册、制度、会议纪要、FAQ 和历史项目中找材料，还要自行判断版本、权限和适用范围。

AI 组织上下文

召回、聚合、标注线索

召回相关知识，聚合相似片段，并附带来源、引用、版本线索和风险提示。

接入后

输出进入上下文卡

输出不再只是聊天回答，而是进入可复核、可确认的上下文卡。

人审边界

最终判断仍需确认

AI 不直接给最终业务结论，也不替业务负责人确认知识是否适用。

这一屏的产品判断是：RAG 不是终点，它只把知识变成候选上下文；可信工作台要继续处理来源、权限、版本、引用、适用范围和人审边界。

05｜核心产品对象

知识不是答案，上下文才是工作台里的对象。

项目 1 的关键不是多做几个 AI 能力点，而是定义清楚知识进入工作台后由哪些产品对象承接、校验、确认、复用和更新。

知识来源

Knowledge Source

承接：知识检索、版本管理、资料来源管理

它是什么
文档、制度、会议纪要、FAQ、项目资料和历史案例，带来源、权限、版本和更新时间。
它不是什么
不是直接交给模型自由使用的原始材料堆。

可信上下文卡

Context Card

承接：引用溯源、搜索与引用结果、证据片段

它是什么
带来源、引用、权限、版本、适用范围和风险提示的候选上下文。
它不是什么
不是最终答案，而是可被检查和确认的工作材料。

知识任务

Knowledge Task

承接：知识任务问答、Agent 执行过程、工具调用、上下文记忆与人工确认

它是什么
把复杂知识请求拆成可追踪的过程，包括检索、引用、上下文组织、工具调用和人工确认。
它不是什么
不是单轮聊天，而是可维护的知识工作流。

行动简报 / 工作台任务

Action Brief / Workspace Task

承接：项目复盘、经验沉淀、待确认事项

它是什么
经过确认的上下文进入方案、复盘、任务或协作空间。
它不是什么
不是由 AI 直接完成的结果，而是下一步行动的输入材料。

复核记录 / 知识更新

Review Record / Knowledge Update

承接：badcase / eval、评估看板、版本回滚与知识更新

它是什么
记录哪些上下文被使用、哪些被修正、哪些进入 badcase / eval，哪些需要更新知识来源。
它不是什么
不是简单日志，而是让工作台持续维护的反馈机制。

页面不是知识展示层，而是可信上下文的工作区。

界面要让知识被检索、引用、确认，并进入复盘、任务和协作工作区。以下原型展示这套机制如何落到具体页面。

07｜产品架构判断

不要让 Agent 裸连知识库，先建立可信上下文层。

企业知识不能直接作为 Agent 的自由输入。Agent 要使用知识，必须经过可信上下文、任务编排、人审确认和反馈回流。

企业知识任务 Agent 工作流架构

围绕真实知识任务，架构将用户输入、Agent 编排、可信上下文、工具调用、人审确认与经验沉淀组织在同一条工作流里。

产品架构的关键不是让 Agent 读得更多，而是限制它只能使用经过上下文处理、可引用、可追溯、可确认的候选知识。

08｜产品演进路径

不是从 RAG 一步跳到 Agent，而是先让上下文可信。

V1 / V2 / V3 的演进不是功能越堆越多，而是产品可信度和工作流承接能力逐步增强：先能找，再能可信使用，最后进入可维护的知识任务。

从知识检索到 Agent 工作流的产品演进

这条演进路径不是从 RAG 直接跳到 Agent，而是先解决“找得到”，再解决“敢使用”，最后让可信上下文进入可维护的知识任务、复盘和持续更新。

09｜验证方式 / 边界

验证不是看回答像不像，而是看依据是否可信。

答案能生成，不代表上下文可信。验证要看关键知识能否找到、引用能否复核、权限和版本是否正确、适用范围是否匹配，以及高风险内容是否进入人审。

01｜验证输入 候选上下文与 Agent 输出

包括引用片段、适用范围、上下文卡、知识任务输出和需要确认的行动材料。

02｜验证维度 依据是否可信

检查召回质量、引用证据、权限版本、适用范围和人审边界。

03｜问题识别 找到不可用的知识使用

识别过期版本、引用缺失、无权限内容、场景不适用或未确认动作。

04｜处理动作 修正并留下记录

进入评估集、复盘修正、版本回滚、知识源更新和人审规则调整。

05｜持续回流 更新规则和知识源

把问题结果回流到下一轮上下文生成、评估规则和知识维护。

闭环判断 验证不是给回答打分，而是判断这段知识是否能被找到、引用、复核、授权使用，并在出错后回到知识源和上下文规则中。

验证维度

召回质量、引用证据、权限版本、适用范围、人审边界和问题回流。

典型问题

过期版本、引用缺失或无法定位、无权限内容、场景不适用、不可复核答案、未确认动作。

处理动作

进入评估集、复盘修正、版本回滚、知识源更新、人审规则调整。

评估与迭代看板

看板用于追踪问题样例、验证维度、版本修正和知识更新，让可信上下文可以持续维护。

这套验证边界的重点不是追求回答更像答案，而是确保每一次知识使用都能回到来源、权限、版本、适用范围和人审责任。

10｜项目总结

不是知识问答机器人，而是知识进入可信工作流的机制。

这个项目的核心不在于让 AI 多回答几个问题，而在于定义：哪些知识可以进入上下文，哪些上下文可以被引用，哪些内容必须经过人确认后才能进入任务、复盘和持续更新。

企业知识进入可信工作流的闭环机制

从知识来源到可信上下文，再到工作流承接和复核更新，形成一条可引用、可追溯、可校验、可确认的产品机制。

什么时候需要可信上下文层？

  • 涉及指定资料，要能回到来源。
  • 涉及业务判断，要能确认适用范围。
  • 涉及组织知识，要能管理权限和版本。
  • 涉及持续使用，要能进入评估、回滚和知识更新。

这个项目的边界

这是产品级原型与机制设计，不是企业生产系统交付。

  • 不声称真实企业生产部署。
  • 本原型阶段不展开完整权限、审计、多用户和系统集成。
  • 不自动写入、删除或发布内容。
  • 不让 AI 替代业务负责人做最终判断。
  • 不让 Agent 直接读取全部企业知识库。

它服务的不是“提问”，而是判断、复盘和行动

项目负责人 / 产品经理、新接手成员、管理者 / 决策参与者、运营 / PMO / 知识管理角色，都通过它确认依据、复盘经验和推进下一步行动。

  • 项目负责人 / 产品经理
  • 新接手成员
  • 管理者 / 决策参与者
  • 运营 / PMO / 知识管理角色

可维护机制：任务和记忆有边界，版本和判断有记录，错误和回归有闭环，人工确认有检查点。

与项目 2 的边界

项目 1 处理的是企业知识如何进入可信工作流：把历史资料、经验和判断转化为可检索、可引用、可复盘的上下文。

项目 2 处理的是业务信号如何进入责任流程：把新产生的反馈、会议结论和需求线索转化为可确认、可拆解、可执行的任务。

一个解决“知识如何可信使用”，一个解决“信号如何进入责任链”。

这个项目的产品判断不是“让 AI 回答得更多”，而是让企业知识在被使用之前，先变得可引用、可追溯、可校验、可确认。
