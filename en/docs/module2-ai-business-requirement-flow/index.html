2.1 Cross-conversation linking and task recovery

What links Friday’s follow-up to Wednesday’s warehouse commitment for RET-001?

  1. CONV-003 Current follow-up
  2. CONV-002 Prior check commitment
  3. RET-001 Same return
  4. CASE-001 Recover the service goal

Why link it to RET-001?

  • The records belong to the same customer and the same RET-001.
  • CONV-002 contains an explicit warehouse-check commitment.
  • Unconfirmed receipt and a missing check record match the unfinished issue.

When should automatic linking stop?

  • A similar follow-up concerns a different return.
  • The commitment cannot be verified as belonging to RET-001.
  • Business-object relationships conflict.
  • Insufficient linking evidence → Keep pending confirmation. Do not act on another return.

AI interprets “you said you’d check” and proposes a candidate link. Business relationships locate the records; trusted rules explain why receipt still needs verification. Tools check commitments and facts within the customer’s access scope. Similar wording does not prove a link, and the LLM must not fill missing facts.

2.6 LangGraph / Dify technology selection

LangGraph state orchestration is the proposed choice.

Sustained Waiting
Retain the service goal, known results and Plan v1 while WH-201 waits for external feedback.
Event-driven resumption
After linking the warehouse event to the task, Warehouse Agent continues checking with prior context retained.
Plan updates
Service Orchestrator Consume verified results before changing assignments and branches.

LangGraph | Proposed choice

Application control over waiting-task state, resumption entry points and remaining plan branches meets this scenario’s needs.

Dify | Visual alternative

Quickly validate standard Agents, tool queries and relatively fixed workflows. Branching and waiting need implementation-specific evaluation; no claim that Dify cannot support them.

Key trade-off: This scenario needs detailed application control over state, pause / resume, result handling and branching. LangGraph offers persistence and pause / resume mechanisms. Application logic must still define event mapping, deduplication, parallel-result aggregation and duplicate-task prevention, then verify resumption correctness.

No live LangGraph runtime or enterprise API is connected. Runtime event resumption remains untested. Persistence, business mapping, deduplication and branches await a minimal mock workflow implementation. This is product design and simulated state, with no runtime execution test results.

Official mechanism references: LangGraph state persistence, Interrupts and resumption; Dify Agent node and Visual workflows.

5.3 What business risks did the two rule failures expose?

BC03 · H02

Repeated warehouse event: deduplicated, yet completed and replanned again

Input conflict
WH-201 is Completed and Plan v2 is active. The same processed event arrives again; a valid receipt record exists.
Initial failure
FAIL: still outputs complete_warehouse, plan_v2. Although check requests are 0, both update intents recur.
Cause
