01 | Business Problem

The enterprise problem is not missing knowledge,but knowledge that cannot be trusted in use.

Enterprise documents, policies, meeting notes, project materials, and historical experience are rarely absent. The real breakpoint is that even when AI finds knowledge, people still cannot tell where it came from, whether it is current, who can use it, and whether it fits the current judgment.

Scattered Sources

Found does not mean usable.

Product manuals, policies, meeting notes, project materials, and FAQs live in many places. A single search rarely restores the full evidence chain.

Version Constraint

Seen does not mean valid.

Plans, policies, and workflows change. Without version and update time, AI-organized content can only stay at the reference level.

Scope Fit

Relevant does not mean applicable.

The same knowledge may only apply to a specific customer type, product version, region, or workflow stage. It cannot directly enter business judgment.

Traceability Gap

Used does not mean reviewable.

Without source, permission, citation, and human review entry, AI output is hard to review and hard to carry into workspace tasks.

What enterprises truly lack is not more answers, but trusted context that supports judgment, review, and action.

08 | From Concept to a Local Runnable Prototype

How was this chain built?

This is not a tech stack description. It is an Architecture Review of the local prototype: define the knowledge boundary first, prove the minimum loop, and return the answer to human judgment.

Design Decision 01 | Local-First

Why choose a local chain instead of cloud APIs?

Constrain the knowledge boundary before validating whether the AI knowledge loop is trustworthy.

Problem Background

The prototype needs to validate a trusted knowledge chain, not the upper bound of model capability. An enterprise knowledge workspace must first prove that documents can be indexed, retrieved, cited, and reviewed locally before chasing a stronger model.

Alternative

Alternative A: Use cloud API / cloud embedding for faster speed and stronger model capability. Alternative B: Build a local-first MVP to validate data boundaries, controllable logs, and citation answer behavior first.

Decision

Documents, embeddings, indices, conversion cache, and logs stay local; Ollama handles local model calls. The data boundary and call chain are controlled first, then the answer is tested for whether it can return to source.

Implementation Evidence

The prototype runs on a 2020 Intel i5 MacBook Pro / 16GB / no GPU, with local execution, local indexing, and local retrieval. The local chain validates whether ingestion → embedding → Chroma → retrieval → citation answer can run repeatedly. This is a product-level demonstrable MVP, not an enterprise production deployment.

Trade-off & Risk

It sacrifices part of speed and model capability in exchange for documents not leaving the machine, controllable logs, traceable badcases, and reviewable results. This is a low-spec MVP trade-off, not a rejection of future cloud capability.

Future Direction

Not implemented in MVP: cloud models, permission systems, audit logs, and system integration should be evaluated after the local retrieval + citation chain becomes stable.

Design Decision 02 | Minimum Loop

Why prove the minimum loop before building a full Agent?

Validate the context layer before discussing Agent, Tool, or action capabilities.

Problem Background

If the project starts with a full Agent / Planning / multi-tool workflow, it hides the most basic questions: can documents be indexed, can questions be retrieved, and can answers return to source? Without trusted context, Agent summaries, suggestions, and actions have no stable basis.

Alternative

Alternative A: Build a full Agent workflow with Planning, Tools, and automated actions from the start. Alternative B: First prove that the retrieval layer, citation layer, and human review can close the loop reliably.

Decision

First run the chain: local documents → document ingestion and conversion → chunk → embeddinggemma → Chroma → top_k 5 → qwen3:0.6b → FastAPI GUI. More complex Agent capability is discussed only after this chain works.

Implementation Evidence

Obsidian Markdown / local documents enter the indexing chain; Chroma stores chunks + embedding + source metadata; FastAPI GUI displays retrieval results, cited passages, and answers.

Component Responsibility

  • embeddinggemma: moves documents into a retrievable representation instead of leaving them as a file pile.
  • Chroma: stores chunks, embeddings, and source metadata so retrieval can return to source.
  • qwen3:0.6b: generates a reviewable draft from retrieved context rather than freely guessing.
  • FastAPI GUI: turns indexing, retrieval, and citation review into a product surface that can be demonstrated and discussed.

Trade-off & Risk

The implementation complexity is reduced to prove the AI product loop first. Planning, multi-tool collaboration, and automated actions are intentionally out of scope to avoid packaging unstable context as automation.

Future Direction

Not implemented in MVP: Memory, Tool, Workflow, and Agent action should enter the next stage only after retrieval + citation becomes stable.

Design Decision 03 | Read-Only by Default

Why stay read-only instead of auto-write or auto-action?

Writing into enterprise knowledge must be governed more carefully than answer generation.

Problem Background

Auto-write, delete, sync, and publish may look more Agent-like, but they amplify the risk of false retrieval, Router misjudgment, and unclear user intent.

Alternative

Alternative A: Enable write / delete / sync / publish to make the prototype feel like an autonomous action system. Alternative B: Keep the MVP read-only and route every write action through preview and human confirmation.

Decision

The default boundary is read-only. Write actions must go through preview + human confirmation. The prototype proves reviewability before actionability.

Implementation Evidence

The MVP validates indexing, retrieval, cited answers, and human review only. It does not automatically write, delete, sync, or publish content.

Trade-off & Risk

This sacrifices automation in exchange for preventing the knowledge base from being polluted by accidental writes. Read-only by default is an Agent product boundary, not an unfinished feature.

Future Direction

Not implemented in MVP: write-back should become an independent workflow with diff, confirmation, and rollback before it is gradually opened.

Design Decision 04 | Proof Boundary

What does this local prototype prove, and what does it not prove?

Honest boundaries build more trust than packaging the MVP as a full enterprise system.

Proven

  • Local documents can be indexed.
  • Questions enter the retrieval chain before answer generation.
  • Answers carry source path, title, passage, and source.
  • Users can return to the original document for review.
  • AI output can serve as judgment material.

Not Proven

  • This is not a production-grade enterprise system.
  • It does not prove permissions, audit, multi-user, or system integration are complete.
  • It does not prove model quality has reached production standard.

Boundary Purpose

The boundary makes the work more credible: it clarifies which capabilities have run, and which remain engineering and productization problems for later stages.

Local Docs → Local Model Calls → Local Index → Reviewable Retrieval → Cited Answer → Human Judgment

09 | From Documents to Reviewable Answers

How was this retrieval chain designed?

This section focuses on the retrieval layer trade-offs: the goal is not to stuff more documents into the model, but to connect source admission, chunking, retrieval range, citation, and refresh into trusted context infrastructure.

Design Decision 05 | Trusted Context

Problem Background

The question is not whether an Agent can read documents. The issue is that raw documents have not yet entered a checkable context layer; free access creates ambiguity around source, version, permission, and applicability.

Alternative

Alternative A: Give Agent direct file access for a smoother surface. Alternative B: Build a retrieval layer + citation layer first, then let the Agent consume trusted context.

Decision

Establish retrieval + citation before Agent summarization, organization, and suggestions. The Agent input is not a file pile, but source-backed context fragments that can be inspected.

Implementation Evidence

Answers are based on retrieved passages instead of letting the model guess freely. The retrieval chain first turns documents into reviewable context, then passes them to the answer model for organization.

Trade-off & Risk

This sacrifices the surface fluency of direct chat in exchange for source traceability and reviewability. The design point is not the RAG label, but giving context permission to enter business judgment.

Future Direction

Not implemented in MVP: Agent action should be connected only after citation answer is stable, avoiding decisions based on naked knowledge-base access.

Design Decision 06 | Source Admission

Problem Background

The key is not how many formats can be read, but which materials are allowed into the index. Knowledge-base quality starts with scope; wrong sources pollute every downstream retrieval and answer.

Alternative

Alternative A: Scan every file to maximize coverage. Alternative B: Read only configured source ranges after source admission, then run ingestion.

Decision

The prototype supports md / txt / docx / pdf / pptx, but reads the allowed indexing scope from configuration instead of scanning the whole machine.

Implementation Evidence

Source admission happens before ingestion; it covers common knowledge carriers such as notes, policies, proposals, and slide decks.

Trade-off & Risk

No full-disk scan. This avoids temporary files, private files, outdated materials, and irrelevant content entering the knowledge base. This is source governance and scope control, not a file-format showcase.

Future Direction

Not implemented in MVP: permissions, directory-level policies, source_type, and project_name filters can be added after the source boundary is stable.

Design Decision 07 | Chunk Strategy

Problem Background

Chunking affects retrieval quality, indexing cost, and whether an answer can be reviewed. This project needed a stable, explainable cut before optimizing chunk intelligence.

Alternative

Alternative A: Smaller chunks, larger chunks, semantic chunk, or section-aware chunk. Alternative B: Use a fixed strategy first for reproducible MVP validation.

Decision

The MVP does not yet implement semantic chunk or section-aware chunk. It uses chunk_target_chars 1200 / chunk_overlap_chars 150.

Implementation Evidence

The value is chosen to preserve the semantic completeness of policy clauses, approval conditions, and project descriptions.

Trade-off & Risk

Too small cuts definitions, conditions, and exceptions; too large introduces noise and weakens retrieval control. overlap 150 keeps cross-paragraph context.

Future Direction

Not implemented in MVP: later iterations can explore title hierarchy, document sections, and semantic boundaries.

Design Decision 08 | Retrieval Range

Problem Background

Retrieval count is not “more is better.” Noisy context can make an answer look complete while mixing sources and weakening credibility.

Alternative

Alternative A: Increase top_k, or introduce rerank / hybrid search / MMR / metadata filter. Alternative B: Keep retrieval simple and bounded for the MVP.

Decision

The MVP has not introduced rerank / hybrid search / MMR. It sets top_k 5 to validate the retrieval + citation minimum loop first.

Implementation Evidence

The answer model receives a limited, reviewable set of candidate passages instead of too much context at once.

Trade-off & Risk

Too few results may miss evidence; too many create noisy context and source-confused answers. top_k is answer quality control, not just a retrieval parameter.

Future Direction

Not implemented in MVP: rerank, metadata filter, and hybrid search can be added later, but they are not claimed as current capabilities.

Design Decision 09 | Citation / Refresh

Problem Background

A trusted answer must solve two separate problems: whether the answer can be traced, and whether the knowledge state is current.

Alternative

Alternative A: Show only the generated answer, or append new chunks without clearing old ones. Alternative B: Make citation and path refresh core mechanisms.

Decision

Citation displays source path, title, passage, and original source. When a document updates, old chunks are deleted by path and the index is rebuilt.

Implementation Evidence

Citation solves answer traceability; path refresh solves stale knowledge state. The answer is not the endpoint; returning to the original document for review is the endpoint.

Trade-off & Risk

Refresh sacrifices some indexing speed for knowledge-state consistency, preventing old policies or old project descriptions from polluting new answers.

Future Direction

Not implemented in MVP: version records, change diff, rollback, and audit trail can be layered on after the refresh mechanism is reliable.

Source Scope → Ingestion → chunk → embedding → Chroma → top_k Retrieval → citation answer → path refresh

10 | From Trusted Context to Agent Judgment

Why not send every problem to an Agent?

In enterprise knowledge workflows, Agent is not the default answer. The real product judgment is deciding when to retrieve, when to organize, when to enter Workflow, and when to stop before human confirmation. RAG / Retrieval / Citation is the input governance layer for Agent, not the final goal.

Design Decision 10 | Context Before Agent

Why should an Agent not read the knowledge base directly?

Agent should consume verified context, not the entire knowledge base.

Problem Background

If an Agent directly reads the full knowledge base, source, version, permission, and applicability become unclear. The answer may sound natural, but the business cannot review it.

Alternative

Alternative A: Agent directly reads all documents or queries the vector store and decides evidence by itself. Alternative B: Agent consumes only the trusted context produced by the retrieval + citation layer.

Decision

Agent does not directly consume the knowledge base. It consumes retrieved passages, source path, title, cited source, and reviewable evidence produced by the retrieval + citation layer.

Implementation Evidence

Verified Pipeline: Obsidian Markdown / local documents → ingestion → embeddinggemma → Chroma → top_k retrieval → citation answer → human review.

Trade-off & Risk

This sacrifices part of answer fluency in exchange for source traceability, answer reviewability, and badcase localization.

Future Direction

Not implemented in MVP: Agent should be built on trusted Context and take responsibility for summary, organization, review, suggestion, and task generation only after retrieval + citation reliability is stable.

Design Decision 11 | Route by Confidence

Why should not every request enter Agent?

Enterprise requests belong to different product paths, not one universal Agent path.

Problem Background

Knowledge lookup, policy search, evidence confirmation, project review, action suggestions, knowledge-base updates, and approval publishing are different task paths.

Alternative

Alternative A: Route everything to Agent and let the model decide the next step. Alternative B: Route by confidence, then enter Retrieval / Citation Answer / Agent Summary / Workflow / Human Confirmation.

Decision

Not every request should enter Agent: information lookup → Retrieval; evidence confirmation → Citation Answer; content organization → Agent Summary; project review → Review Workflow; knowledge update → Preview + Human Confirmation; high-risk action → Workflow + Audit.

Implementation Evidence

Earlier Agentic RAG design materials already included Router, search_docs Tool, Memory, and Agent Core as design directions. The current MVP has validated Retrieval + Citation, but does not claim Router / Workflow / Agent Action as complete implementations.

Trade-off & Risk

Router mistakes affect the entire downstream flow. Low confidence should trigger clarification or fallback to Retrieval instead of forcing the request into Agent.

Future Direction

Not implemented in MVP: route confidence, fallback, human confirmation, and route-level evaluation require a verifiable question set and failure-recovery rules.

Design Decision 12 | Confirm Before Action

Why should Agent not act automatically by default?

The highest risk is not the answer, but turning the answer into action.

Problem Background

Write-back, delete, sync, publish, policy update, and approval can affect downstream business processes. Enterprise AI products must govern answers and actions separately.

Alternative

Alternative A: Execute action immediately after the answer for a more automated assistant experience. Alternative B: Keep the default read-only; write actions must go through preview → diff → confirmation → execute.

Decision

First prove that answers are reviewable, then discuss automated action. The current boundary is read-only, and all write actions require preview → diff → confirmation → execute.

Implementation Evidence

The current MVP does not auto-write, delete, sync, or publish. The answer is only a reviewable draft, and the user must be able to return to the source before making judgment.

Trade-off & Risk

This sacrifices automation experience to avoid polluting the knowledge base when sources are insufficient, retrieval is wrong, or user intent is unclear.

Future Direction

Not implemented in MVP: Action should enter independent workflow orchestration only after preview / diff / rollback / audit trail are established.

Design Decision 13 | Memory Last

Why put Memory at the end?

Long-term memory becomes an asset only when write conditions are controlled.

Problem Background

Many Agents add long-term Memory early. In enterprise knowledge scenarios, low-quality Memory amplifies old rules, expired knowledge, unconfirmed judgments, and temporary wording.

Alternative

Alternative A: Let Agent auto-save long-term Memory for a more continuous and personalized experience. Alternative B: First validate retrieval / citation / refresh / read-only boundary, then design Memory write conditions.

Decision

Memory is not a first-stage capability. First establish trusted context, traceable citation, and confirmed write-back; then decide what information deserves to enter long-term Memory.

Implementation Evidence

The current MVP focuses on Retrieval, Citation, Refresh, and Read-only Boundary. Memory, Tool, Workflow, and Agent Action belong to the next stage and are not described as implemented.

Trade-off & Risk

This temporarily sacrifices continuous personalization to prevent low-quality information from becoming a hidden pollution source for future answers and actions.

Future Direction

Not implemented in MVP: Memory needs write conditions, conflict detection, human confirmation, update, deletion, and version management instead of append-only storage.

The point of this section is not to prove “I understand Agents,” but to prove that I know when not to use an Agent. Agent becomes eligible for enterprise workflow only when context is trustworthy, routing is clear, and action boundaries are contained.

The core of this project is not making AI answer more questions. It defines which knowledge can enter context, which context can be cited, and which content must be confirmed by people before it enters tasks, recaps, and continuous updates.

When is a trusted context layer needed?

  • When specified materials are involved, the system must return to source.
  • When business judgment is involved, the scope must be confirmed.
  • When organizational knowledge is involved, permission and version must be managed.
  • When knowledge is used continuously, evaluation, feedback, and knowledge update must exist.
